                    evidence summary for report export3. Workflow, step by step
1. Device →  IoT Core. ESP32 publishes to freshtrace/device/{device_id}/telemetry
over MQTT/TLS, authenticated with a per-device X.509 certificate provisioned through IoT Core's
device registry. This is already how you're connected — nothing changes here.
2. IoT Rule fan-out. One SQL-style IoT Rule (SELECT * FROM  
'freshtrace/device/+/telemetry' ) triggers three actions on every message, with no
code running in the rule itself:
Action A →  Lambda (lightweight validation — schema/range checks from Phase 10 §5.2 of
the roadmap). Valid messages are re-published to a validated  topic; invalid ones go to
an SQS dead-letter queue with the rejection reason attached, so nothing is silently dropped.
Action B →  Kinesis Data Firehose, which buffers and batch-writes to S3 as the permanent
raw archive (partitioned by device/date). An AWS Glue Crawler run over this bucket registers
a schema, so you can run ad-hoc Athena SQL over historical raw data — a nice thing to demo
if a judge asks "can you show me the raw sensor data for this window."
Action C →  Kinesis Data Streams, one stream (or one shard per device if you want to future-
proof for a fleet), which is the low-latency path the processor actually consumes from.
3. ECS Fargate Processor runs as a long-lived service with a Kinesis Client Library consumer. This is
the right shape for your sketch's original idea — Fargate rather than Lambda specifically because
Phases 11–17 need continuous per-device state (running baseline, EMA, volatility window) that's
awkward to carry across stateless Lambda invocations. It:
Maintains session lifecycle and baseline (Phase 11) — hot state (running mean/stddev, last
EMA value, last N readings for outlier checks) lives in DynamoDB, keyed by device_id , so
the processor can restart or scale to multiple tasks without losing state.
Writes filtered/processed readings to Timestream (this is your time-series query backend
for the dashboard's charts).
Runs the biochemical engine, thermal engine, onset state machine, RUL estimator, and
fusion logic (Phases 12–16) in-process, since they all operate on the same per-reading
stream.
Writes session records, current state snapshots, and evidence events to Aurora
PostgreSQL (relational, good for the joins the report export needs).
Publishes every named event (Phase 17) to EventBridge.
4. EventBridge fan-out. From one event bus:
A rule matching SPOILAGE_ONSET_CONFIRMED  or *_RISK_HIGH  → SNS → email/SMS
or a webhook into a Slack channel for the demo ("look, it just paged us live").
A rule matching any event →  also lands in CloudWatch Logs for observability.This is also where you'd hang a Step Functions workflow later if you wanted a multi-step
response (e.g. auto-flag a shipment for inspection) — you don't need to build that for the
hackathon, but having EventBridge in place means you can say "the architecture supports it"
credibly.
5. API layer, two paths for two purposes:
API Gateway + Lambda for anything request/response — historical queries, the report
export endpoint (Phase 18's /devices/{id}/report ), device list.
AppSync for anything that should update live on screen — current risk state, onset alerts.
AppSync subscriptions push straight to the dashboard the moment Aurora/Timestream is
written, no polling loop, no manual WebSocket plumbing.
6. Amplify Hosting + Cognito. The React dashboard (Phase 19 of the roadmap) is hosted on Amplify,
with Cognito handling auth if you want a login screen for the demo (or skip Cognito entirely if the
hackathon demo is single-tenant and auth isn't the point — don't spend hackathon hours on login
screens unless judges specifically care).
7. (Optional, high-value if time allows) Bedrock. On report export, send the session's event list +
current state object to Claude via Bedrock with a prompt like "explain in plain English why this
shipment is at X% risk, referencing these events" — turns your evidence log into a paragraph a
non-technical buyer/inspector can read. This is a strong differentiator for a food-safety-facing
product and it's a genuine, non-gimmicky use of an AI service, which tends to score better with
judges than a bolted-on chatbot.
4. Why this mapping (for your pitch / judging Q&A)
Every AWS service here is doing the job it's actually built for, not used as a generic substitute for
something simpler — that's the difference between "we used a lot of AWS" and "we used AWS well."
Be ready to explain why Timestream vs. Aurora, and why Fargate vs. Lambda for the processor, in
exactly those terms (state, latency, query shape) — judges in an AWS-branded hackathon usually
probe this specifically.
IoT Core →  Rules Engine →  parallel fan-out is the idiomatic AWS IoT pattern (this part of your
original sketch was already correct) and costs you nothing extra to implement since it's
declarative, not code.
DynamoDB for hot state / Timestream for time-series / Aurora for relational is polyglot
persistence used correctly — each store holds the data shape it's best at, which is a legitimate
architectural story, not overengineering, given the actual access patterns (per-device point
lookups, time-range scans, and relational joins for reporting are three different query shapes).
EventBridge as the seam means your evidence system (which the roadmap already treats as a
first-class differentiator) is wired into the rest of AWS's ecosystem instead of being a dead-endtable.
5. Security & IAM (worth having answers ready for, even
if not fully implemented by demo time)
Each IoT device uses a unique X.509 certificate with an IoT policy scoped to publish only on its
own topic (freshtrace/device/${iot:Connection.Thing.ThingName}/telemetry )
— prevents one compromised device from publishing as another.
Fargate task role: least-privilege — read from its Kinesis stream, read/write its DynamoDB table,
write to Timestream and Aurora, publish to EventBridge. No S3 access needed (that's Firehose's
job, not the processor's).
Lambda validation function role: publish to the validated  topic and SQS DLQ only.
Aurora and DynamoDB in private subnets; only the API Gateway/Lambda and AppSync resolvers
(via VPC access if needed) can reach them — the dashboard never talks to the database directly.
6. Build order (mirrors the roadmap's dependency-first
sequencing, now AWS-specific)
1. IoT Rule + Lambda validation + DLQ (you already have the IoT Core connection — this is the
hardening layer).
2. Firehose →  S3 archive path (cheap to stand up, unblocks nothing downstream but gets your audit
trail running from day one).
3. Kinesis Data Streams + Fargate consumer skeleton (just prove messages flow end-to-end before
adding any scoring logic).
4. DynamoDB hot-state schema + baseline/filter logic inside Fargate.
5. Timestream writes for processed readings.
6. Biochemical/thermal/onset/RUL/fusion logic inside the same Fargate service (this is where the
roadmap's Phases 12–16 math actually lives).
7. Aurora schema for sessions/events/state snapshots + EventBridge publishing.
8. API Gateway + Lambda for REST endpoints.
9. AppSync subscriptions wired to Aurora/Timestream writes.
10. Amplify dashboard, built against real data from step 8–9 onward.
11. SNS alert rule + CloudWatch dashboard (fast to add, strong demo payoff).
12. Bedrock narrative summary, if time remains.
